# Phase 1 — Schemas and mock data — Interview Notes

## 1. What was built

Covers **R1** (ingest client financial data, schema-validated) and **R2** (mock CRM API data):

- `schemas/client.py` — `Holding`, `Account`, `Transaction`, `ClientProfile` Pydantic v2 models, `extra="forbid"` so unknown fields are rejected rather than silently dropped. `ClientProfile.from_file()` loads + validates a JSON file and converts any JSON or schema error into a `ClientDataValidationError` with a readable, field-by-field message — never a raw traceback.
- `schemas/crm.py` — `CrmProfile` model (risk tolerance, goals, last contact, advisor notes).
- `errors.py` — `WealthAdvisorError` base class and `ClientDataValidationError`.
- `scripts/generate_mock_data.py` — deterministic generator (fixed seed) for 5 client files, the CRM records file, and `expected_anomalies.json`.
- Five client fixtures, each exercising a different edge case from `planning.md` §7, plus unit tests proving the "done when" criterion: all five either load correctly or fail with a clear message.

## 2. Approach used and why

Schema-first: no agent code exists yet, but the contract every future agent depends on does. `extra="forbid"` is deliberate — in a finance product, a field the schema doesn't know about should be surfaced immediately (typo, API drift, unexpected PII) rather than silently ignored.

The validation-error path is a first-class feature, not an afterthought: `from_file()` catches both "file doesn't parse as JSON" and "JSON parses but doesn't match the schema" and turns both into the same typed, readable exception. This is what makes `client_005.json` (intentionally malformed — missing `transaction_id`, `amount` as a string) a useful test case rather than a bug: it proves the system fails loudly and clearly instead of crashing or silently accepting bad data.

Mock data is generated by a script with a fixed seed rather than hand-written JSON, so it's reproducible and so a reviewer can regenerate it and get byte-identical output — but the four anomalies in `client_002` (large transfer, duplicate payment, spending spike, concentration) are *not* random; they're deliberately injected so the Phase 9 evaluation script has guaranteed ground truth to score against.

## 3. Technology used and why

| Choice | Why | Alternative considered |
|---|---|---|
| Pydantic v2 (`model_validate`, `ConfigDict(extra="forbid")`) | Fast (Rust core), gives structured, field-level errors via `.errors()`, is the schema layer the rest of the stack (LangGraph state, tool results) also uses | `dataclasses` + manual validation — more code, worse error messages; `marshmallow` — slower, no v2-era ecosystem fit |
| `Literal[...]` for enums (asset class, account type, transaction type, risk tolerance) | Closed vocabularies validate at parse time; a typo'd category fails immediately instead of silently becoming an "unknown" bucket later | Plain `str` fields — simpler but pushes validation to every downstream consumer |
| A custom `ClientDataValidationError` wrapping `pydantic.ValidationError` | Keeps Pydantic's exception type out of the public API — callers (CLI, agents) catch one domain exception, not an SDK-specific one | Letting `ValidationError` propagate raw — couples all callers to Pydantic's exception shape |
| A generator script with a fixed seed, not hand-written fixture JSON | Reproducible, easy to regenerate/extend, and the "clean" client's transactions are realistically varied instead of suspiciously uniform | Hand-written JSON fixtures — more direct control but no reproducibility story, and tedious to extend |

## 4. Alternative approaches considered

- **Make all 5 client files schema-valid (push "malformed" to the analysis layer).** Considered, since `planning.md`'s edge-case table treats negative amounts/duplicate IDs as data-quality flags handled later by the Analyzer, not load-time failures. Rejected for `client_005` specifically: the Phase 1 "done when" criterion is "all five files load **or fail with a clear validation message**," which only means something if at least one file actually exercises the failure path. `client_005` was chosen to make that explicit and testable now, rather than deferring all failure-path testing to Phase 2/3.
- **Validate at the dict level with `jsonschema` instead of Pydantic models.** Rejected — Pydantic gives typed Python objects for free, which every downstream agent/tool needs anyway; a separate JSON Schema would just be a second contract to keep in sync.
- **Store `amount`/`value`/`balance` as `Decimal` instead of `float`.** `Decimal` is more correct for currency but adds JSON (de)serialization friction for a project where this is mock, non-regulated data and no real money moves. Flagged as a known shortcut — would switch to `Decimal` first in a real production version (see `planning.md` §9.15 "what I'd do next").

## 5. Expected interview questions

- Why `extra="forbid"` instead of the Pydantic default of silently ignoring unknown fields?
- Walk through what happens, end to end, when `client_005.json` is loaded — what exception is raised, and what does the caller see?
- Why are the anomalies in `client_002` hardcoded rather than randomly generated like the rest of the data?
- Why `Literal` types for category/account-type/transaction-type instead of free-text strings?
- What's the trade-off of using `float` instead of `Decimal` for monetary values here?
- How would you version this schema if a new required field needed to be added later without breaking old mock data files?

## 6. Scenario-based questions

- **"A real CRM integration starts sending an extra field we don't have in `CrmProfile`."** What happens today with `extra="forbid"`, and is that the right behavior for a CRM feed specifically (vs. client financial data)?
- **"You get a client file where `amount` is `"1,200.50"` (a formatted string) instead of a number."** Trace exactly what error message the user sees and whether it's actionable.
- **"The evaluation script in Phase 9 needs ground truth for anomaly detection."** Why was `expected_anomalies.json` generated alongside `client_002` instead of being hand-labeled separately after the fact?
- **"A teammate wants to add a new required field to `Transaction`."** What breaks across the 5 mock client files, and what's the safe order of changes to avoid a half-broken repo?
